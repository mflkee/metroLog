# Концепт: конфигуратор пресетов дедлайнов

## Задача

Нужна новая вкладка в `Настройках`, где можно собирать и редактировать пресеты дедлайнов.

Под пресетом понимается именованный набор правил расчета сроков по процессам.
Главный сценарий:

- администратор или разработчик создает пресет дедлайнов;
- при создании папки пользователь выбирает этот пресет;
- все новые процессы внутри папки получают дедлайны не из захардкоженных значений, а из выбранного пресета;
- стартовый системный пресет называется `ТЮНГД`.

## Почему это нужно

Сейчас ремонтные дедлайны в коде фактически зашиты:

- ремонт: `sent_to_repair_at + 100 дней`;
- получение в Ленске: `arrived_to_lensk_at + 5 дней`;
- входной контроль: `actually_received_at || registration_deadline_at + 40 дней`;
- оплата: `incoming_control_at || control_deadline_at + 70 дней`.

Это работает только для одного бизнес-сценария. Если объект или договор живет по другой схеме сроков, приходится менять код, а не настройки.

## Новый объект: пресет дедлайнов

### Сущность

Нужна отдельная сущность `DeadlinePreset`.

Минимальные поля:

- `id`
- `code`
- `name`
- `description`
- `is_active`
- `is_system`
- `sort_order`
- `repair_total_days`
- `registration_after_arrival_days`
- `incoming_control_after_receipt_days`
- `payment_after_control_days`
- `created_by_user_id`
- `updated_by_user_id`
- `created_at`
- `updated_at`

### Первый системный пресет

Нужен системный пресет:

- `name`: `ТЮНГД`
- `code`: `tyungd`
- `description`: базовый пресет текущих сроков ремонта
- `repair_total_days`: `100`
- `registration_after_arrival_days`: `5`
- `incoming_control_after_receipt_days`: `40`
- `payment_after_control_days`: `70`

Это должен быть стартовый пресет, который повторяет текущее поведение системы.

## Новая вкладка в настройках

### Название

Новая верхнеуровневая вкладка или секция в `Настройках`:

- `Пресеты`

### Что должно быть внутри

Вкладка `Пресеты` должна быть отдельной от тем, папок и информационной панели.

Содержимое:

- список всех пресетов;
- карточки пресетов;
- кнопка `Создать пресет`;
- форма создания и редактирования;
- быстрый просмотр состава дедлайнов;
- признак системного пресета;
- признак использования в папках.

### Структура карточки пресета

В карточке пресета:

- название;
- описание;
- бейдж `Системный`, если это системный пресет;
- сколько папок используют этот пресет;
- сроки в компактном виде:
  - ремонт,
  - получение,
  - входной контроль,
  - оплата;
- действия:
  - `Редактировать`,
  - `Дублировать`,
  - `Отключить`,
  - `Удалить`.

### Ограничения

- системный пресет `ТЮНГД` нельзя удалить;
- пресет, который уже назначен хотя бы одной папке, нельзя удалить без явного переназначения;
- неактивный пресет нельзя выбирать для новых папок, но он остается у уже существующих папок;
- если пресет используется, его изменение не должно задним числом молча пересчитывать активные процессы.

## Интеграция с папками

### Создание папки

В модалке создания папки добавить новое поле:

- `Пресет дедлайнов`

Поведение:

- поле обязательно;
- по умолчанию выбран `ТЮНГД`;
- рядом показывается краткое превью:
  - ремонт: `100 дн.`
  - получение: `5 дн.`
  - входной контроль: `40 дн.`
  - оплата: `70 дн.`

### Редактирование папки

При редактировании папки поле тоже должно быть видно.

Безопасное правило для первой версии:

- смена пресета влияет только на новые процессы;
- уже созданные ремонты не пересчитываются автоматически;
- для активных ремонтов продолжают жить те дедлайны, которые были рассчитаны на момент создания.

Это важнее, чем “магическая” массовая переоценка, потому что пересчет может неожиданно поменять просрочки и журнал.

## Как папка должна хранить пресет

У папки должно появиться:

- `deadline_preset_id`
- `deadline_preset_name`
- `deadline_preset_snapshot_json`

Почему нужен snapshot:

- если пресет потом отредактируют, старые процессы в папке не должны задним числом менять поведение;
- snapshot позволяет понять, по каким конкретно правилам считались сроки у этой папки на момент выбора пресета.

## Как применять пресет в рантайме

При создании ремонта система должна брать не жесткие `100/5/40/70`, а текущий snapshot папки.

Пример:

- `repair_deadline_at = sent_to_repair_at + repair_total_days`
- `registration_deadline_at = arrived_to_lensk_at + registration_after_arrival_days`
- `control_deadline_at = anchor + incoming_control_after_receipt_days`
- `payment_deadline_at = anchor + payment_after_control_days`

Если у папки почему-то нет пресета:

- использовать fallback `ТЮНГД`
- и желательно логировать это как техническое отклонение

## Права доступа

Для первой версии:

- `DEVELOPER` и `ADMINISTRATOR` могут создавать и редактировать пресеты;
- `MKAIR` и `CUSTOMER` не управляют глобальными пресетами;
- любой пользователь, у которого есть право создавать папки, может выбрать один из активных пресетов при создании папки.

## Миграция

Нужна безопасная миграция:

1. создать таблицу пресетов дедлайнов;
2. создать системный пресет `ТЮНГД`;
3. добавить поля пресета в папки;
4. всем существующим папкам назначить `ТЮНГД`;
5. сохранить snapshot `ТЮНГД` в каждую существующую папку.

Так система сохранит текущее поведение без регрессии.

## UX первой версии

### В настройках

- новая вкладка `Пресеты`;
- вверху кнопка `Создать пресет`;
- ниже список карточек пресетов;
- редактирование через модалку или раскрывающуюся карточку.

### В папках

В форме создания папки:

- поле выбора пресета;
- компактная памятка по срокам;
- если пресет `ТЮНГД`, можно показать бейдж `Стандартный`.

## Что не делать в первой версии

Чтобы не перегрузить релиз, в первой версии не нужно:

- массово пересчитывать старые ремонты при изменении пресета;
- делать отдельные пресеты для разных типов процессов, кроме ремонта;
- вводить сложную матрицу правил по ролям или организациям;
- делать пользовательские локальные пресеты на уровне аккаунта.

## Рекомендуемый порядок реализации

1. Добавить модель и миграцию `DeadlinePreset`.
2. Добавить связь пресета с папкой и snapshot в папке.
3. Перевести расчет ремонтных дедлайнов с хардкода на snapshot папки.
4. Добавить вкладку `Пресеты` в `Настройки`.
5. Добавить выбор пресета в создание и редактирование папки.
6. Проверить, что существующие папки после миграции работают как раньше через `ТЮНГД`.

## Минимальный итоговый результат

После первой поставки должно быть возможно:

- открыть `Настройки` -> `Пресеты`;
- увидеть системный пресет `ТЮНГД`;
- создать новый пресет с другими сроками;
- создать папку и выбрать для нее нужный пресет;
- создать ремонт в этой папке и получить дедлайны из выбранного пресета, а не из захардкоженных значений.
