Recon of the remaining interactive widgets on the two task pages: the only hand-rolled dropdown is `EmojiPickerButton` (open state + an absolute panel, used twice on `TaskDetailsPage`), the autocompletes (`AutocompleteInput`/`AutocompleteTextarea`) are hand-rolled comboboxes that already carry `role=listbox`/`aria-selected`/keyboard navigation, and the other controls are native `<select>` elements (8 on `TasksPage`, 1 on `TaskDetailsPage`) which are accessible and not the source of the defect class. Recommendation: adopt `dropdown-menu` for the emoji picker and leave the native selects alone;  Not pilot-scoped after all: `EmojiPickerButton` is a **shared** component with 19 call sites across five pages (`TaskDetailsPage`, `RepairsPage`, `VerificationPage`, `EquipmentDetailsPage`, `EquipmentPage`), so adopting `dropdown-menu` there would change pages outside the pilot and break the "only the pilot pages import them" invariant. It also interacts with modals: a portalled Radix menu inside a Radix dialog would be `aria-hidden` by the dialog's focus scope, which the bespoke `Modal` does not do. Decision: the `dropdown-menu` adoption is deferred, not forced - it needs either a fleet-wide rollout decision or a task-page-local variant.
